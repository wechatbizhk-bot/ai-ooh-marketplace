# 3dNakedEye — AI OOH Marketplace (Hong Kong + Thailand · four languages)

A two-sided, trilingual web platform where **advertisers** create and book location advertising and **landlords** list locations, approve campaigns and earn revenue — with an **operator console** for verification, moderation, scheduling, settlement and audit.

Positioning: *“Create, book, pay for and measure location-based advertising — from one platform.”*

Built as a **static site with no build step and no dependencies**: open `index.html` and it runs. Data, payments and device telemetry are seeded/simulated, so the whole transaction can be demonstrated end to end.

---

## 1. Run it

**Option A — no server** (everything except live AI, street-map tiles and the Google Translate widget):

```
double-click index.html          (or drag it into a browser)
```

**Option B — bundled Node server** (recommended: adds live DeepSeek AI, payment intents and http/https for Google Translate):

```bash
node server/deepseek-proxy.mjs
# → http://localhost:8787/index.html
```

Optional environment variables (a `server/.env` file is read automatically):

| Variable | Purpose |
| --- | --- |
| `DEEPSEEK_API_KEY` | live AI Studio generation **and** grounded answers from the site assistant (`/api/chat`) |
| `STRIPE_SECRET_KEY` | real Stripe PaymentIntents |
| `PAYPAL_CLIENT_ID`, `PAYPAL_SECRET` | real PayPal orders (`PAYPAL_BASE` for live vs sandbox) |
| `CRYPTO_WALLET_ADDRESS` | your receiving address for crypto invoices |
| `PAY_CURRENCY` | defaults to `HKD` |
| `CONTACT_EMAIL` | where enquiries are delivered — defaults to `commercialisation.ai@gmail.com` |
| `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_ID` | WhatsApp Cloud API credentials; without them `/api/whatsapp/send` returns the `wa.me` deep link |
| `WHATSAPP_TO` | business number enquiries are forwarded to — defaults to `85297398018` |
| `WHATSAPP_API_VERSION` | Cloud API version — defaults to `v21.0` |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS` | real mail delivery (implicit TLS, port 465); without it every message lands in `server/outbox` as `.eml` |

Without keys every provider answers in **simulated** mode, so the checkout, the enquiry pipeline and the assistant still work end to end.

## 4. Two markets, proximity search and availability states

- Every location carries **real WGS-84 coordinates**; landlord-registered sites are placed at their district centre with a deterministic offset.
- **Street map (OpenStreetMap tiles) when reachable, offline schematic map otherwise** — identical pins, colours and distances, so the demo never depends on the network. The provider switch (`auto` / `streets` / `schematic`) is in the marketplace control bar.
- **Near me**: browser geolocation, with a landmark picker (Tsim Sha Tsui, Central, Mong Kok, Sha Tin, Kwun Tong, Causeway Bay, Tung Chung, Tuen Mun) when permission is refused.
- **Radius**: 1 / 2 / 5 / 10 / 25 km ring, optional “within radius only” filter, and **distance sorting** using the haversine formula.
- **Availability states** for the selected campaign window (dates + number of days + category):

| State | Meaning |
| --- | --- |
| **Available** | ≥ 40% of the loop free on every requested day |
| **Partly booked** | 12–40% free — a smaller share of voice can still be bought |
| **Fully booked** | < 12% free — effectively sold out for those dates |
| **Restricted for me** | the location blocks the advertiser's category, so it is hidden regardless of availability |

Availability combines each site's rolling occupancy, a deterministic per-day variation (weekends busier) and **anything already committed in the session** — so booking a site visibly moves it towards “fully booked”, and the filter chips recount the map in real time.

### Design and light theme

The interface is a light theme: white surfaces, soft shadows, a corporate blue/violet accent set, and light map canvases with the same availability colours. Two surfaces stay deliberately dark because of what they represent — the video stage (a still frame reads as video) and the hologram preview with its QR tiles (black pixels are what make the hologram illusion work). All colours come from the token block at the top of `assets/css/style.css`; the light layer immediately below it re-colours the handful of components that were originally written for a dark canvas, so re-theming again is a token change plus that one block.

The home page also carries an **industry reference platforms** section — The Trade Desk, Amazon DSP, Adobe Advertising Cloud, StackAdapt and MediaMath (now part of Infillion) — each linking to the source, with a note that these are independent third parties and that 3dNakedEye is not affiliated with them. The Trade Desk card also links to their own video channel, and the explainer's reference library (see §6) covers DSP, programmatic and pDOOH material.

### Advertiser console and automation (added)

Two consoles complete the loop for advertisers:

- **`adsmanager.html` — Ads Manager in the shape of Meta Ads Manager / Google Ads.** A KPI strip (spend, verified plays, modelled impressions, QR clicks, CPM, CTR, conversions, cost per conversion), a campaign table with on/off toggles, delivery state, budget, pacing, and **vs. benchmark** columns; ad sets grouped by placement; a creative table with format and hologram-compliance state; an audience table built from venue footfall; a **placement planner** (the keyword-planner analog — type *bakery*, *clinic*, *students* and get districts, venues and live sites with estimated footfall, modelled impressions and day rates); benchmark reporting; Google-Ads-style **recommendations** that apply real changes (raise share of voice, add a hologram variant, extend the flight by 7 days, switch on coupon tracking, test a second district); delivery **diagnostics**; bulk pause/resume; and a five-step creation wizard (objective → audience & placement → budget & schedule → creative → review) that writes a real campaign and fires the approval emails.
- **`automation.html` — email automation.** Twelve triggers across all three parties — new booking paid, approval requested, approved, rejected, payment received, campaign live, campaign ending, weekly report, monthly statement ready, device offline, low occupancy, placement plan summary. Each rule has an on/off switch, recipient group, timing (instant / daily / weekly digest) and a template; the outbox lists every message with a rendered preview, an **.eml download** you can open in a mail client, and CSV export; a "test the flow" strip fires any trigger against live data; templates are browsable in all four languages; settings cover sender name, reply-to, per-party opt-outs and digest choice.

The notification engine (`assets/js/notify.js`) is wired into the real flow: paying at checkout queues booking, payment and approval-request mail; a landlord decision queues the approved or rejected mail; the operator can run weekly digests. Messages render in the **recipient's language** (market default, or a per-party preference). The server exposes `POST /api/notify/email` — SMTP when `SMTP_HOST`/`SMTP_USER`/`SMTP_PASS` are set (implicit TLS, port 465), otherwise every message is written to `server/outbox` as a real `.eml` file and reported as queued, so the automation can be demonstrated and audited offline. `GET /api/notify/outbox` lists what was written.

### The reference pages

Three pages carry the supplier's own data rather than marketing copy, because these are the questions that decide a purchase:

- **`catalog.html` — the product catalogue.** Every model, every figure: LED count, resolution, unit size, input voltage, power rating, brightness, storage, content control and net weight, series by series, plus the engineering-vs-compact comparison sheet, the matrix builds (1×3 → 3×3, up to 6912 × 6912 px fused) and the accessory list. - **`dimension.html` — the dimension calculator.** The supplier's calculation workbook reduced to two numbers per size class — the display size and the centre-to-centre spacing when units are spliced into one image — and the arithmetic on top of them. Enter a wall (or a quantity), pick the model class, and the page returns columns, rows, units, covered area, fused pixel size, power with 20 % headroom, the comfortable viewing distance and the content brief the designer needs. An operator who reads it can register a device, group a matrix, upload a clip and schedule it without guessing.


## 6. Front of site: FAQ, enquiry, WhatsApp, the assistant and membership

Everything a visitor needs before they buy, driven from one configuration block (`LG_CONFIG.contact`, `.social`, `.chat`, `.membership`, `.auth`).

**FAQ — one corpus, three surfaces.** `window.LG_FAQ` in `data.js` holds 81 questions in 6 groups (hologram and holobox hardware, content and production, operation/safety/maintenance, the 3dNakedEye service, account/membership/privacy); the wording lives in `i18n.js` as `faq.<id>.q` / `faq.<id>.a`, so every question exists in English, 繁體中文, 简体中文 and ไทย. ## 8. LBS in the product: Location-Based Services

The marketplace explains the concept and then applies it, in both directions the category defines:

- **What LBS means** — a collapsible explainer at the top of `marketplace.html`: *Location-Based Services use a device position to decide what to show it.*
- **How the position is established** — the four signal sources, named and explained: **GPS satellites** (metre-level outdoors), **cellular tower signals** (indoors, lower precision), **Wi-Fi triangulation** (inside malls and offices), **Bluetooth beacons** (room-level, “standing at this counter”).
- **Pull — the user asks**: the advertiser searches the map for inventory near a shop, sets a radius, sorts by distance and books what is free; the same shape as searching for a nearby coffee shop.
- **Push — the system offers**: the network pushes a different message when a condition is met, like a local weather alert or a store promotion.
- **Push trigger simulator** — six triggers (rain, lunchtime, weekend, event crowd, beacon entry, peak commute). Each shows the signal that detects it, the action taken (“switch creative variant”), and the actual nearby locations that would receive it, filtered by the current radius and availability window.
- **Occupied vs available** — every site is colour-coded for the chosen dates: **Available** (≥40% free), **Partly booked** (12–40%), **Fully booked** (<12%), **Restricted for me** (category blocked), with live counts on the map legend and the filter chips, plus availability and distance columns in the table view.

## 12. The user manual deck (PowerPoint)

A 40-slide user manual and introduction travels with the platform. It sits **beside this folder**, in the workspace: `ppt/3dnakedeye-user-manual/` (source) and `3dNakedEye-User-Manual-and-Introduction/3dNakedEye-User-Manual.pptx` (delivery). It is **generated, not hand-drawn**:

- Source of truth: `ppt/3dnakedeye-user-manual/deck.pptd` plus 40 `.page` files (PPTD v2, 960 × 540 pt, the *Course Workshop* palette: paper `#F7F4EB`, ink `#243F35`, accent `#447A62`, field `#E5EBDD`).
- Generator: `node _verify/make-user-manual-deck.cjs`. Every text box is sized from its own content by a copy of the PPTD text estimator (glyph widths, greedy wrap, 0.88 width reserve for real-Arial slack), and the layouts shrink their own font until the copy fits — so a wording change can never silently overflow a slide.
- Contents: cover → what the platform is → the measured-salience argument → the role map → getting started → the advertiser journey (choose and price, AI studio, creative preview, book/pay/publish) → the advertiser portal → the landlord portal → the operator console → how to read the page reference → a full slide for each of the twelve core pages → eight grouped slides covering the other twenty-four pages → languages and translation → the assistant, the FAQ corpus and the sixteen email rules → the engineering record and the honest limits → testing, demo shortcuts and deployment → close.
- Export: `pptd_render` writes `3dNakedEye-User-Manual-and-Introduction/3dNakedEye-User-Manual.pptx` (40 slides, 712 editable objects, no rasterised text).
- Verified three ways: `pptd_check` (0 revisions, 0 advisories — text-fit, bounds, duplicate ids, composition repetition); the exported package re-checked for banned supplier wording; and `_verify/deck-render-check.ps1`, which opens the deck in PowerPoint and compares every text frame's **real** rendered bounds (BoundWidth/BoundHeight) against the slide edge and against every other text frame — 598 frames, no off-slide text and no text-on-text collision.
- Known behaviour of the estimator: a query-string-heavy line (e.g. the `?market=th, ?radius=5…` deep-link bullet) is laid out by PowerPoint in three lines where the estimator predicts two. The box is the last element on its slide, so nothing is obscured — recorded here rather than hidden.

How the translation is produced and checked:

- **One string catalogue.** `node _verify/make-user-manual-deck.cjs --dump` walks every slide and writes the **521** distinct visible strings to `_extract/ppt-i18n/strings.json`. Only the visible slide text is translated; speaker notes stay as document metadata.
- **The website's own vocabulary leads.** `_verify/deck-i18n-glossary.cjs` reads the reviewed dictionaries in `assets/js/i18n.js` (4 094 keys × 繁體/简体) and `assets/js/i18n.th.js`, then matches **402 English phrases that actually occur inside the deck strings** — so 廣告客戶、場地擁有人、戶外廣告、播放佔比 and their Thai equivalents are the same words the website uses. 26 deck strings were word-for-word identical to a reviewed website string and reuse it verbatim.
- **Translated in parallel chunks, then unified.** Fifteen payloads (5 languages × 3 chunks of ~174 strings) wrote id-keyed replies; `_verify/deck-i18n-merge.cjs` merges them by id (it only reports unless `--write` is passed — it overwrote two reviewed files once, and that guard is the fix). Each language then had a **terminology review pass** that unified concepts the chunks had rendered differently: Japanese `場地オーナー`→`場所オーナー` (16 strings, a Chinese-only slip), Thai `ผู้ดูแล`→`ผู้ดูแลแพลตฟอร์ม`, Korean `장소 소유자`→`매체사` and `명세서`→`정산서`, Vietnamese `tỷ lệ chia sẻ` split into `thị phần hiển thị` (share of voice) versus `tỷ lệ chia doanh thu` (revenue split) — two concepts that had been sharing one phrase.
- **Checked, not hoped.** `_verify/deck-i18n-status.cjs` proves every dictionary still has its 521 keys, nothing added or dropped; `_verify/deck-i18n-qa.cjs` learns the Simplified-only character set from the site's own 繁體/简体 pairs (506 characters) and fails a 繁體 string that uses one — it caught **幂** where Traditional Chinese writes **冪**; `_verify/deck-i18n-terms.cjs` checks 943 (繁體) and 596 (Thai) glossary occurrences with whole-word matching and reports the terms that drift.
- **Layout is recomputed per language, not inherited.** Because a translated box must be measured against the text that will actually appear, `M()` measures the *translated* string (the English decks are byte-identical to before). Two bugs came out of this: the table header row had a fixed 14 pt height (a Thai header "ผู้ดูแลแพลตฟอร์ม" needs two lines), and the two-column layout did not reserve room for its own note. Both are fixed, and every edition now passes `pptd_check` with **0 revisions and 0 advisories**. Measurement reserves are per language (0.88 English, 0.86 Vietnamese, 0.92 for the CJK/Thai editions, which the estimator already treats conservatively because every non-Latin glyph counts as a full em).
- **Rendered and measured in PowerPoint.** Each edition is exported and then opened by `_verify/deck-render-check.ps1`, which compares every text frame's real rendered bounds against the slide edge and against every other text frame: **598 frames per edition, no off-slide text and no text-on-text collision**. Fonts were chosen from what is actually installed (Meiryo is not on this machine; Yu Gothic is, so Japanese uses it).
